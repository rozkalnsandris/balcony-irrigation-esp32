# HA bounded watering protocol — build-only candidate (#69, #71, #73, #75)

Source proposal for RPi5_main#1555. No flash, live MQTT, pump command, or HA cutover is authorized by this file or its merge.

## Build isolation

Normal esp32_ci and esp32_ota environments retain the legacy behavior. Only esp32_ha_bounded_candidate sets BALCONY_HA_BOUNDED_PROTOCOL=1 and is built by CI; it has no OTA configuration. Never upload this build as a test. A later owner-approved deployment requires a frozen build/artifact and coordinated retirement of legacy start publishers and schedules. In candidate mode all legacy start/extend paths are denied: plain HA ON, laist, laist_N. Existing OFF/stop and read-only diagnostics remain. The existing HA discovered switch can still display an ON control; it is not an admissible start path in candidate mode and must be replaced/hidden in the later HA source outcome.

## Wire contract (candidate only)

The existing HA pump command subscription is used; no new inbound subscription. All outgoing protocol responses are best-effort QoS0, non-retained, on `balkons/ha45/reply`. HA must subscribe/establish its receive context before requesting an offer. Do not issue these messages to a live broker as a source test.

| Message | Meaning |
| --- | --- |
| ticket45: + 16 lowercase hex characters | One correlated request, not an actuator command |
| offer2: + request ID + colon + 24 lowercase hex ticket + colon + 40 lowercase hex firmware revision + colon + 10 sample codes + :off | One atomic fresh-scan offer; 10 s ticket lifetime from scan start |
| start45: + exact offered 24 lowercase hex characters | Single-use candidate start; 32 bytes total |
| on: + exact ticket | Device software accepted start after GPIO write |
| off: + exact ticket | Device software executed OFF; not physical feedback |

Publisher must use non-retained commands. The existing MQTT adapter rejects retained deliveries and unsupported QoS/envelope lengths; the bounded parser additionally requires exact topic, length and lowercase hex, no trimming or embedded NUL. MQTT 3.1.1 does not expose the publisher retain flag to every already-subscribed client; broker-side authorization and non-retained publisher behavior still matter. QoS1 delivery and DUP flag are not an exactly-once contract. The protocol's single-use ticket handles repeat delivery independent of DUP.

A ticket is 64 bits of per-boot entropy from ESP32 hardware RNG while Wi-Fi is connected, plus a 32-bit sequence that refuses wrap. It is opaque correlation, not a password or publisher authentication. It prevents reuse within a boot, and cross-boot collision is probabilistic (64-bit entropy assumption), not a durable replay database. A newly admitted request revokes the old offer; a recent duplicate does not. The ticket expires 10 s from the beginning of its fresh scan using unsigned monotonic elapsed time; expiry is serviced even when idle. A queued request is valid for less than 5 s from actual callback receipt and its STOP/session epoch must still match. The FIFO dequeue transfers the entire record including receivedAt, rather than defaulting the timestamp to zero (#73). Tickets are invalidated on urgent STOP/OFF, session disconnect/connect, OTA, normal stop or start failure. A duplicate start cannot re-arm, extend, or create another ticket.

Only issue/consume a ticket when the application MQTT session is READY, Wi-Fi connected, pump OFF, no pending urgent STOP, no OTA, no outstanding MQTT outbox or tracked publish. The ticket is consumed before pre-start network work.

### Fresh scan and offer v2 (#71)

On each newly admitted ticket request, invalidate any previous offer, then read all ten enabled MUX channels once using the existing ADC averaging, invalidity and category functions. No retained, previous periodic or partial sample is used. The fixed code order is flowers `1,3,4,5,6,7,8,9,10,12`; `D` = sauss, `W` = mitrs, `M` = videjs, `U` = existing ADC invalid/unavailable classification. Retired channels are never sampled. Unstable/out-of-range ADC input is represented by U, not dry. A floating/disconnected channel can still yield a plausible stable ADC value; this does not prove electrical connectivity or calibration. HA must apply the approved sensor policy to these fresh codes (including the intermediate and degraded guards), not the retained individual HA states.

Require software pump OFF and the relay GPIO readback OFF, ready network, no pending STOP and the same STOP/session epoch before and after each sample; service urgent input and watchdog between samples. Reject partial or wrong-order scan, duration >= 2000 ms, stale queued request, changed epoch, lost readiness, or dirty/unknown firmware revision. A clean full Git revision is mandatory but not cryptographic remote attestation. No offer is produced on failure, and the previous offer remains invalidated. The response is one 104-character non-retained QoS0 message on the existing reply topic, for example `offer2:0123456789abcdef:fedcba987654321000000001:0123456789abcdef0123456789abcdef01234567:DWMUWDWDWU:off` (synthetic identifiers). The ticket and evidence are inseparable in one message. The 10-second TTL includes the scan itself; a successful start must still pass the existing pre-GPIO guard. The OFF indication is software/GPIO evidence, not independent physical pump feedback.

This deliberately supersedes the old 47-character `offer:` format. RPi5_main #1557 is an inhibited reference for the old format: it must remain inhibited and cannot accept v2 without a reviewed source update. No compatibility fallback, second offer topic or new subscription. HA must have established its receive context, match its unique request ID and expected firmware SHA, reject malformed or stale offers, consume a single frozen matching response, and recheck clock/arm/pending/cancellation before dispatch. The scan binds evidence to the ticket and the device's current accepted MQTT session; the ticket invalidates on session/STOP/OTA boundaries. This is not publisher authentication or proof that the host received the first event. A bounded RAM FIFO records the eight most recent admitted request IDs before scanning, even if the scan fails, expires or is canceled. A duplicate in that history is silently rejected before any ticket invalidation, scan, reply or TTL renewal. The history is retained across STOP, expiry, MQTT reconnect and OTA callbacks within the same boot. It is not refreshed on duplicate delivery. After eight other admitted IDs or reboot, an old ID can be admitted again; a delayed first delivery after STOP is also not covered. This is bounded duplicate suppression, not a global replay database or proof of host cancellation. HA must use unique IDs, no request retries, one admission context, and exclusive publisher control. RPi5_main #1561 consumes offer2 and pins the merged #74 revision. This cutoff change requires a new reviewed pin before any release. No live HA integration or runtime timing/transport proof is provided here. Recheck the claimed ticket and all admission conditions immediately before the existing GPIO ON. Candidate planned duration is the remaining part of 45 s measured from device scan start (therefore at most 45 s from HA dispatch; usually slightly shorter than 45 s of actual GPIO ON). No duration override or extension. The existing 180 s absolute session limit remains as a cooperative secondary guard; it is not independent. Candidate #75 adds the loop-independent one-shot described below. Physical cutoff at 45 s remains unproven; no activation authority.

The legacy retained switch ON can precede GPIO ON; it is not a correlated acknowledgement. The candidate queues an on receipt only after GPIO ON and checks the pump state/time first; inability to enqueue invokes local OFF. A normal or urgent stop invalidates the ticket and queues the matching off receipt after GPIO OFF. The reply uses the existing enqueue-only publishMessage interface, not a nested MQTT loop while ON. Connection loss in candidate mode requests immediate OFF when detected and the service loop checks loss as well. If an ACK is lost, delayed or arrives after STOP, it describes a historical software event only; HA must fail closed and use its separately reviewed OFF recovery path. No automatic ON retry. OTA/reboot or disconnect may lose ACK entirely.

## Candidate hardware cutoff (#75)

Only the build-only HA candidate uses a GPTimer alarm, not the default legacy or OTA environments. The pinned platform 55.03.311 supplies Arduino 3.3.11 / ESP-IDF 5.5.5 (prior #74 CI resolved libraries 5.5.5+sha.b774170ff46). Candidate startup preloads the active-low GPIO26 OFF latch before selecting output mode. This does not prove reset/boot/physical NO behavior.

The candidate requires the actual SDK to report CONFIG_GPTIMER_ISR_CACHE_SAFE and CONFIG_GPTIMER_ISR_HANDLER_IN_IRAM enabled, successful 1 MHz hardware timer initialization and watchdog subscription. Absent support or uncertain driver state, refuse offers and starts, never fall back to the cooperative timer. No command-line override of a prebuilt SDK config. The initial PR #76 build with the prebuilt Arduino libraries recorded HA_CUTOFF_ACTUAL_SDK_CACHE_SAFE=NO. The pinned pioarduino 55.03.311 builder supports candidate-only `custom_sdkconfig` and recompiles the IDF libraries via HybridCompile, then compiles the Arduino application against the rebuilt packages. Set only CONFIG_GPTIMER_ISR_CACHE_SAFE=y and CONFIG_GPTIMER_ISR_HANDLER_IN_IRAM=y in the candidate environment. The runtime fail-closed gate is unchanged. CI now requires actual YES, fresh IDF library rebuild evidence, matching generated SDK header values, linked callback and driver ISR in IRAM and guard instance in DRAM; unsupported SDK is a failed candidate build check, not a release pass. Entry/data placement is not full transitive ISR call-graph proof.

HybridCompile modifies the SDK package directory and creates temporary project configuration files. CI therefore builds the candidate in a fresh disposable local Git clone at the checked-out revision with a separate `PLATFORMIO_CORE_DIR`; all legacy and OTA builds use the unchanged default SDK. Only the known generated files are excluded locally in that disposable clone. No repository-wide generated-config ignores, no SDK header patch, no `-D CONFIG_GPTIMER...` workaround and no production package mutation. For manual build-only verification use the same isolated CI recipe; do not run this custom SDK build in the production checkout or shared PlatformIO core. The result is not a deployment artifact approval.

Use a continuously running GPTimer with a single non-reloading alarm per admission. Sample its count before sampling the remaining ticket budget; program that count plus the remaining scan-start cycle budget less a conservative 1000 ms engineering margin. A delay before sampling the budget shortens the alarm. Require the counter to advance, >100 ms remaining alarm lead, <100 ms preparation age, still-valid ticket lifetime and all existing pre-start checks before GPIO ON. Refuse rather than extend or rearm. The margin is a provisional conservative engineering choice, not measured worst-case latency. A successful alarm can therefore stop the pump earlier than the existing cooperative limit.

A short common critical section serializes GPIO26 ON/OFF and the ISR latch; the ISR writes the OFF register and updates only the guard state (no MQTT, logging, heap, timer driver calls). Normal, urgent, disconnect and OTA OFF paths force GPIO OFF and cancel permission. Early cancellation does not reset the alarm; no new admission until that original one-shot callback executes and the main loop reconciles OFF. Driver failure or unexpected IRQ faults the guard until reboot. The main task alone reconciles pump state, epoch, token, statistics and best-effort ACK; after a long stall the reported duration may include time after hardware OFF. Never enqueue ON for an already observed trip; an ON ACK still describes a historical software event, not physical feedback or instantaneous state.

This is independent of the application loop when the hardware, clock and interrupt dispatch remain functional. It is **not** independent of interrupt masking, core lockup, reset, power supply, output driver failure or welded contacts. The pinned build's actual cache flags and ELF evidence, full ISR call/data-path review, no-late-start and stale IRQ fault tests, clock tolerance and measured GPIO/relay release latency remain release requirements. An absolute physical bound under total controller failure requires a separately independent power cutoff with verified tolerance and NO/reset wiring (#2). Any later bench tests must use isolated motor power or a non-actuating dummy load under separate authority; no forced live watering. Keep HA #1561 hard-inhibited.

## HA obligations — not implemented here

Run weather/sensor checks first, then enter one admission lock and establish a new unique request ID and cancellation context. Accept only the first matching v2 offer received in that context within the bounded wait; validate exact identity and fresh codes, freeze it, verify/record the day reservation and recheck safety and clock, then dispatch at most one matching start if still in time. Never refresh a ticket or adopt a new offer for the same attempt. STOP cancels the pending request/admission even before an offer is received; a device can issue a new offer for a delayed request arriving *after* STOP, but that offer cannot revive a canceled HA admission. Prove this race at the HA integration gate; device-side epoch alone cannot distinguish such a delayed request. No real start until this host-side cancellation invariant and sole publisher constraints are established.

Use matching software on/off receipts with fresh session evidence, not a retained switch state alone. Bound ACK wait to <=5 s from start dispatch, and normal OFF deadline no later than 45 s from dispatch; ambiguous result must inhibit future admission and invoke the separately reviewed bounded OFF path. The current physical cutoff, restart-day reservation, device/HA clock validity, HA v2 fresh-offer consumption and real freshness/cancellation evidence, sensor calibration, MQTT publisher/ACL inventory, exclusive legacy scheduler retirement and physical NO wiring remain explicit open gates. This candidate does not implement date policy, weather/sensor gates, HA helper changes, scheduler, permissions, new credentials, or durable daily admission. No new service.

## Offline evidence

Native tests exercise the same whole-record dequeue transfer helper as firmware, including ordinary uptime, exact age boundary, epoch and millis wrap. They also exercise recent-ID rejection before reissue, expiry/cancellation without history reset, failed-scan admission, non-consecutive duplicates, bounded eviction and reboot limits. Candidate cutoff native tests cover shortened budget, millis wrap, late start, timeout before/while ON, cancel, fault and no alarm reuse before callback reconciliation. The CI cutoff contract checks source wiring and SDK/ELF support as above. Existing native tests cover exact payload decoding, default disabled, wrong topic/retained/truncated/NUL/uppercase payload, claim/duplicate/replacement, cancellation/invalidation, expiry and millis wrap, queue age/epoch, and shortened duration. Additional native tests exercise ordered complete scan encoding, explicit unavailable/intermediate values, clean revision format, partial/duplicate/retired channels, epoch/readiness and elapsed-time wrap rejection, and counting scan age against ticket/cycle limits. Existing native tests and source contracts remain in CI; CI additionally compiles the candidate. These tests exercise the policy, not the real broker, callbacks under all transport stalls, physical relay, or HA integration. Verify no-late-start, timing, ACK/STOP interleavings, boot/session entropy and physical isolation before activation. Keep legacy behavior unchanged in the default environments.
